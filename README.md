# Zhao Yun Restaurant Ordering

奥地利餐厅手机和平板点餐系统，包含顾客端、员工看板、管理台、Fastify/SQLite 后端、Android Capacitor 工程和打印机适配层。

## 当前功能

- React + TypeScript 顾客端和管理台
- `motion` React 动效库驱动稳定的 3D 翻面
- 后端真实菜单 seed：111 条菜品、寿司、酒水和咖啡茶数据，三语名称：中文、Deutsch、English
- 手机/平板横屏与竖屏响应式布局
- 菜品详情卡片：点击打开，点击卡面直接进行连续 3D 翻转
- 图片和视频使用同一套翻转交互
- 食材、过敏原、规格、价格、购物车、下单和订单状态
- 服务呼叫、管理台后端订单与服务呼叫看板、媒体上传和打印机发现
- 每台设备单独配置桌号（`?table=` 或管理台连接设置）
- Capacitor Android 测试构建与 kiosk 模式
- 每台设备独立桌号：`?table=` 或首页「设置桌号」，订单、服务呼叫和打印小票都带真实桌号
- 桌台登记与令牌：登记后服务端只接受已登记的桌号，并要求设备带上该桌令牌
- 管理台「订单看板」：全店实时订单、服务呼叫和失败打印任务，可推进状态、取消订单和重新打印
- 按桌账单：按 10% / 20% 税率拆分净额与税额，打印给客人看的账单（非税务收据）
- 餐厅账户：注册、账户名 + 密码登录，账户下管理多个跑堂
- POS 点餐收银（`pos.html`）：跑堂 PIN、菜号点单、送厨、退菜、沽清、桌号锁、外带取餐号、一起结 / 分开结、补打小票、跑堂结算、日结、DEP 交易日志，见 `docs/POS.md`
- 实时同步：POS 下单、开桌、结账、客人扫码下单，管理台和其他 POS 立即刷新；管理台实时看到每个跑堂在哪台设备、开着哪些桌、本班营业额
- 过敏原按奥地利 A–R 字母代码维护，顾客端显示代码和三语说明
- 后端请求 schema 校验、订单状态机、认证限流和生产启动校验
- 公开下单/呼叫接口按设备 IP 限流，避免同一台设备刷单
- 离线订单持久化重试、幂等下单和 LAN ESC/POS 打印代理
- SQLite 一致性备份、integrity_check 和失败打印任务人工重试接口

## 快速开始

```bash
npm install
npm run build
ADMIN_TOKEN='replace-with-a-long-random-token' npm run server
```

浏览器访问：

- 顾客端：`http://127.0.0.1:8787/`
- 管理台：`http://127.0.0.1:8787/admin.html`

每台平板首次使用时设定桌号：用 `http://<服务器>:8787/?table=12` 打开一次，或在管理台
“连接设置”里填写“本机桌号”。桌号保存在该设备本地，之后下单和呼叫服务都用它。

完整 Android SDK、APK 安装、局域网部署和打印机说明见 [INSTALL.md](INSTALL.md)。
正式营业请用 [deploy/](deploy/README.md) 里的 systemd / launchd 单元托管服务和打印代理：
断电或崩溃后必须自动拉起，没人会在营业中去手动敲 `npm run server`。

部署前请先阅读 [INSTALL.md](INSTALL.md) 的生产环境要求；当前版本适合单机/单进程餐厅部署，多实例前需要将认证限流迁移到共享存储。放在反向代理后面时必须把可信代理地址填进 `TRUST_PROXY`，否则限流会把所有请求算成同一个来源。
部署前请先阅读 [INSTALL.md](INSTALL.md) 的生产环境要求；当前版本按单机/单进程餐厅部署设计，多实例前需要将认证限流和公开接口限流迁移到共享存储。

打印任务会按商品的出单档口拆分：厨房、吧台、寿司台和前台分别排队。管理台配置打印机时，可为每台设备选择打印语言（中文 / Deutsch / English）和字符编码（UTF-8 / GB18030 / Shift-JIS / CP437）；订单会保留中德英名称，由各打印机独立转换后输出。当前输出是标准 ESC/POS 订单制作单，不是整本菜单双面菜单；正式上线前必须用实际打印机做中文编码、纸宽和裁切测试。

## 桌号配置

每台点餐设备必须绑定自己的桌号，否则订单会全部记到占位桌号 `08`：

1. 首选：给每台设备配置带桌号的入口地址，例如 `http://192.168.1.20:8787/?table=12`；桌号会写入本机并在之后的普通访问中沿用。
2. 备选：在首页点「设置桌号」输入 1-8 位字母或数字（例如 `12`、`T-3`、`TERRASSE`）。
3. 未配置的设备会在首页显示红色提示，方便开台前检查。

桌号只保存在设备本地，服务端按请求中的桌号入库、分单和打印。

### 桌台登记（防止冒用桌号）

在管理台「连接设置 → 桌台」登记桌号后，服务端进入受控模式：

- 只接受已登记且启用的桌号，其他桌号返回 `403`。
- 请求必须带 `x-table-token`，顾客端从入口链接的 `k=` 参数获取并保存。
- 每桌的入口链接形如 `http://192.168.1.20:8787/?table=12&k=<令牌>`，可直接做成书签或二维码。
- 令牌可随时更换；更换后旧链接立即失效，需要重新分发。

没有登记任何桌台时保持开放模式，全新安装可以先跑起来再逐桌收紧。

## 餐厅账户

管理台第一次打开时注册餐厅账户：账户名（可以用邮箱）和密码，之后用它登录管理台、
给 POS 平板配对。跑堂都在这个账户下面：在「设置 → 跑堂与 POS 设备」里添加，每人一个
PIN。密码存在你自己的后端（D1 或本机 SQLite）里，存的是 PBKDF2 哈希，不是密码本身；
登录换回来的是一个有效 12 小时的会话令牌。改密码会让其他已登录的设备重新登录。

一个部署就是一家餐厅：第一个账户注册后，注册就关闭了。网站是公开的，谁先打开管理台
谁就能注册，所以上线后请立刻注册。以前设过的管理密码会自动变成账户 `admin`，密码不变。

忘了密码，用 `ADMIN_TOKEN` 重设：在「连接设置」里填上令牌，再到「设置 → 账户」里重设。
令牌本身也还能直接当经理用——墙上那种配一次就不再动的平板还是用令牌。

## 角色与操作记录

除了餐厅账户，还有三个共享令牌，各自一个角色（在「连接设置」里填）：

| 角色 | 环境变量 | 能做什么 |
|---|---|---|
| 经理 | `ADMIN_TOKEN` | 全部：菜单、价格、打印机、桌台、结账、看操作记录 |
| 服务员 | `STAFF_TOKEN`（可选） | 订单看板、结账、处理服务呼叫、重打小票；**不能**改菜单或价格 |
| 厨房 | `KITCHEN_TOKEN`（可选） | 只看订单、推进订单状态 |

只配 `ADMIN_TOKEN` 时行为和以前完全一样。控制台会按角色只显示该角色能用的标签页，
服务员和厨房设备不会看到用不了的入口。

所有带令牌的**写操作**和被拒绝的越权尝试都记进操作记录（经理在「连接设置」页查看）：
时间、角色、设备 IP、动作和关键字段。共享令牌记不到具体是谁，但能回答
「谁的角色在什么时候改了什么」——共用一个令牌时这一点尤其要紧。

## 订单看板

管理台新增「订单看板」标签页，数据全部来自服务端，因此任意一台管理设备都能看到全店状态：

- 进行中的订单：推进 `新订单 → 制作中 → 可上菜 → 已完成`，或取消订单。
- 服务呼叫：标记已处理。
- 打印失败：显示失败次数和错误原因，可重新排队打印。

顾客端的「员工看板」仍然只显示本机订单，用于单机演示；正式营业请使用管理台看板。

## 结账与税率

收银在 POS（`http://<服务器>:8787/pos.html`）：管理台添加跑堂和 PIN，平板用餐厅账户配对后，跑堂登录点单、送厨、结账。POS、管理台和顾客菜单实时同步（`/ws`）。
一起结或按菜分开结，现金 / 银行卡 / 代金券可混合；每张小票不可修改，错了由经理冲销。
管理台「桌位」里的账单可以直接打印给客人看，「去收银」打开 POS。详见 `docs/POS.md`。

接入 fiskaly 签名之前，小票印 `TESTBELEG – NICHT SIGNIERT`，还不是 RKSV 合规收据。

菜单价格是含税价。默认税率为餐食 / 寿司 10%、酒水 20%，可在商品编辑器按商品调整（10% / 13% / 20%）。默认值按常见的奥地利餐饮税率预填，正式使用前请让税务顾问确认。

## 过敏原

商品编辑器用勾选框维护奥地利 A–R 过敏原代码（A 含麸质谷物、B 甲壳类、C 蛋、D 鱼、E 花生、F 大豆、G 奶、H 坚果、L 芹菜、M 芥末、N 芝麻、O 亚硫酸盐、P 羽扇豆、R 软体动物）。后端只接受这 14 个代码，保存时去重并按菜单顺序排序；顾客端详情页显示代码加当前语言的名称。

## 交互约定

菜单卡片的实际操作顺序是：点击列表卡片打开详情，再点击详情卡面翻转；正面和背面均可点击返回另一面，加减数量和加入购物车按钮不会触发翻转。语言在首页选择，进入菜单后沿用，当前语言会持久化到本地设备。详情每次打开都从数量 1、未选选项开始；相同菜品加相同选项会累加到同一条购物车行。

顾客端的“员工看板”只显示本机下过的订单和呼叫，离线也能看；全店订单看板在管理台“订单看板”，
状态变更走后端状态机，对所有设备生效。

## 契约

请求体的 schema 只有一份：`src/contracts.js`。服务端用它做运行时校验，前端的 TypeScript 类型描述同一个形状，
`packages/contracts/test/parity.test.ts` 负责保证两边不漂移——类型能表达的值必须通过校验，schema 拒绝的值类型也必须拒绝。
改了一边忘了另一边，测试会红。

## 已知边界

LAN 打印代理已完成任务租约、失败重试和人工重试接口，但真实打印纸张输出仍需连接具体型号的实体打印机验证；USB/Bluetooth 后端代理需要对应驱动或 Android 端执行。iOS 工程、签名 IPA 和生产级 Device Owner 配置未在本仓库中声称已完成。

管理台是一个餐厅一个密码，没有账号体系：操作记录能追到角色和设备，追不到具体是谁。
多人共用时，密码泄露只能靠改密码。
尚未实现，正式营业前需要评估：

- 支付：系统不处理任何支付方式，也不生成税务收据；账单只是内部结账凭据。
- 分单结账：目前按桌整单结账，不支持按人或按菜品拆分。
- 认证限流和公开接口限流都是单进程内存状态；本项目按单机单进程部署设计，多实例部署前需迁移到共享存储。
- 桌台令牌保存在设备 localStorage，防的是误用和随手冒用，不能防拿到链接的人。
- 顾客端「员工看板」的状态变更只作用于本机，不写回服务器。
- 角色是三个共享令牌，不是个人账号：操作记录能追到角色和设备，追不到具体是谁。多人共用一个令牌时，令牌泄露只能靠更换。
