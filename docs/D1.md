# D1

The schema and the seeded menu are migrations now. The API still runs as the
Node/Fastify server against a local SQLite file; moving it onto Workers is the
next step, and nothing below waits on that.

## What you need to provide

1. **Account.** `npx wrangler login`, then `npx wrangler whoami` prints the
   account id.
2. **A database.**

   ```
   npx wrangler d1 create zhaoyun-ordering
   ```

   It prints a `database_id`. Put it in `wrangler.toml` in place of
   `REPLACE_WITH_DATABASE_ID`. That id identifies the database; it is not a
   credential, and it belongs in the repository.
3. **For CI to deploy**, a `CLOUDFLARE_API_TOKEN` repository secret with
   **D1:Edit** and **Workers Scripts:Edit**, created at
   https://dash.cloudflare.com/profile/api-tokens. A repository secret is the
   only place it needs to exist — it should not be pasted anywhere else.

## Applying the migrations

```
npx wrangler d1 migrations apply zhaoyun-ordering --local    # a throwaway copy on your machine
npx wrangler d1 migrations apply zhaoyun-ordering --remote   # the real database
```

`--local` runs against the same engine D1 runs in production, so it is a
rehearsal rather than an approximation. Check what landed:

```
npx wrangler d1 execute zhaoyun-ordering --local \
  --command "SELECT COUNT(*) AS products, COUNT(DISTINCT category) AS categories FROM products"
```

Expect 111 products across 19 categories.

## Regenerating the migrations

Both files are generated, never hand-edited:

```
npm run d1:migrations
```

`0001_init.sql` is read out of `sqlite_master` after the Node server has built
its own schema, and `0002_seed_catalog.sql` out of the products it seeds. So the
D1 schema cannot drift from the one the integration tests run against, and the
product ids match the catalogue the app ships offline — an order placed on a
tablet that has never reached the server still names a product D1 knows.
`npm run server:test` fails if either file is stale; it also applies both to an
empty database and diffs the result against the server's own.

The seeded rows carry a fixed `created_at`/`updated_at` so the generated file is
byte-identical every run. The restaurant's own edits overwrite it.

## What moving the API to Workers still needs

- `server/database.mjs` uses `node:sqlite`, which is synchronous. D1 is not, so
  every query and the transactions around them have to be rewritten as async.
- The realtime board is a WebSocket hub inside the Node process. On Workers that
  is a Durable Object, or the board polls.
- Uploaded dish photos are written to disk. On Workers they belong in R2.
- `server/print-agent.mjs` claims print jobs by opening the SQLite file
  directly. It runs next to the printers in the restaurant, so it stays where it
  is and claims jobs over HTTP instead.

## The trade this makes

Today the system keeps taking orders and printing tickets with the internet
down, because the database and the printers are both in the building. Once the
database is D1, an outage stops ordering and printing until it clears — during
service, on a Saturday night, that is the whole operation. Worth deciding on
deliberately rather than discovering.
