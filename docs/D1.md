# D1

The API runs on Workers over D1, in `workers/`. The Node/Fastify server in
`server/` still runs against a local SQLite file and is not going away — it is
what `npm run dev` uses and what keeps working with the internet down.

They are two implementations of one API, so they are held together two ways.
Everything that *decides* something — what an order costs, which status may
follow which, what a product row means to a client — lives once in
`shared/rules.mjs` and is imported by both. Everything else is checked: the
assertions in `shared/contract-suite.mjs` run against the Fastify server in
`npm run server:test` and against the Worker in `npm run worker:test`, and CI
runs both on every pull request. `npm run worker:test` starts `wrangler dev` on
a local D1, which is workerd and the real D1 engine rather than a stand-in, so
it needs no Cloudflare credentials.

## What you need to provide

1. **Account.** `npx wrangler login`, then `npx wrangler whoami` prints the
   account id.
2. **A database.**

   ```
   npx wrangler d1 create zhaoyun-ordering
   ```

   It prints a `database_id`. Put it in `wrangler.toml` in place of
   `REPLACE_WITH_DATABASE_ID`. That id identifies the database; it is not a
   credential, and it belongs in the repository.
3. **For CI to deploy**, a `CLOUDFLARE_API_TOKEN` repository secret with
   **D1:Edit** and **Workers Scripts:Edit**, created at
   https://dash.cloudflare.com/profile/api-tokens. A repository secret is the
   only place it needs to exist — it should not be pasted anywhere else.

## Applying the migrations

```
npx wrangler d1 migrations apply zhaoyun-ordering --local    # a throwaway copy on your machine
npx wrangler d1 migrations apply zhaoyun-ordering --remote   # the real database
```

`--local` runs against the same engine D1 runs in production, so it is a
rehearsal rather than an approximation. Check what landed:

```
npx wrangler d1 execute zhaoyun-ordering --local \
  --command "SELECT COUNT(*) AS products, COUNT(DISTINCT category) AS categories FROM products"
```

Expect 111 products across 19 categories.

## Regenerating the migrations

Both files are generated, never hand-edited:

```
npm run d1:migrations
```

`0001_init.sql` is read out of `sqlite_master` after the Node server has built
its own schema, and `0002_seed_catalog.sql` out of the products it seeds. So the
D1 schema cannot drift from the one the integration tests run against, and the
product ids match the catalogue the app ships offline — an order placed on a
tablet that has never reached the server still names a product D1 knows.
`npm run server:test` fails if either file is stale; it also applies both to an
empty database and diffs the result against the server's own.

The seeded rows carry a fixed `created_at`/`updated_at` so the generated file is
byte-identical every run. The restaurant's own edits overwrite it.

## Deploying

`.github/workflows/ci.yml` has a `deploy` job: on every push to `main` that
passes `checks` and `android`, it applies the D1 migrations and runs
`wrangler deploy`. A pull request build, however green, never runs it — the
`if` on the job is `github.ref == 'refs/heads/main' && github.event_name ==
'push'`, so nothing touches the real database or the live Worker until a
commit lands on `main`.

It needs one thing from whoever owns the Cloudflare account:
`CLOUDFLARE_API_TOKEN` as a **repository secret** (Settings → Secrets and
variables → Actions → Secrets, not Variables), scoped to **D1:Edit** and
**Workers Scripts:Edit** as described above. Without it the job fails at the
first `wrangler` call rather than deploying with no credential.

By hand it is the same two commands:

```
npx wrangler d1 migrations apply zhaoyun-ordering --remote
npx wrangler deploy
```

The admin token is a Worker secret, not a variable, and is set once:

```
npx wrangler secret put ADMIN_TOKEN     # at least 32 characters
npx wrangler d1 migrations apply zhaoyun-ordering --remote
npx wrangler deploy
```

The Worker refuses a token under 32 characters rather than falling back to a
default: a deployed backend with a weak admin token is worse than one that
plainly is not configured yet.

`ADMIN_TOKEN` is optional now. The restaurant's account — registered by
whoever opens the console first, an account name and a password kept as a
PBKDF2 hash in D1 — is the way in; the token is the way back in when that
password has been forgotten (POST /api/account/recover, or the settings when
the console is opened with it), and what a wall-mounted tablet is configured
with. A deployment with neither refuses admin routes with 503 and says so.

Whoever opens a public console first registers the account, and registration
closes after that, so register as soon as the site is live. Configuring
`ADMIN_TOKEN` is what makes that recoverable. A password set at the old
one-password door became the account `admin` (migration 0055).

The live channel (/ws) is a Durable Object, `LiveHub` (workers/live.mjs),
declared in wrangler.toml with its own migration tag; SQLite-backed, which is
what the Workers Free plan offers. It needs no setup beyond the deploy.

## A custom domain

`wrangler deploy` always gives a free `*.workers.dev` address; nothing extra
is needed to use it. A domain the restaurant already owns can point at the
same Worker instead:

1. The domain's DNS has to be on Cloudflare — either bought through Cloudflare
   Registrar, or its nameservers changed at whichever registrar it was bought
   from to the two Cloudflare gives when the domain is added to the account
   (**Websites → Add a domain** in the dashboard). Without this step, Custom
   Domains below has nothing to attach to.
2. **Workers & Pages → ck → Settings → Domains & Routes → Add →
   Custom Domain**, type the domain (`example.com` or a subdomain of it).
   Cloudflare creates the DNS record and issues the TLS certificate itself;
   there is no separate certificate step.
3. Rebuild the APK against the new address (`VITE_API_BASE`, above) once it
   resolves — the old `workers.dev` one keeps working, so this is not
   urgent.

This is a Cloudflare dashboard action against whoever's account owns the
Worker and, if the domain lives elsewhere, an action at that registrar too —
neither is something a repository change can do.

## Roles

`ADMIN_TOKEN` is the manager. Two more secrets are optional and give the other
two roles their own token:

```
npx wrangler secret put STAFF_TOKEN      # waiter tablets
npx wrangler secret put KITCHEN_TOKEN    # the kitchen screen
```

Leave them unset and the deployment has one role rather than three aliases of
it. What each may reach is decided in `shared/rules.mjs` and is the same on
both backends:

| | manager | staff | kitchen |
|---|---|---|---|
| Menu, prices, allergens (`/api/admin/products`) | ✓ | | |
| Printer profiles, tables and their tokens, audit log | ✓ | | |
| Service calls, print jobs, the room view, locking a table, the bill | ✓ | ✓ | |
| Orders and their status | ✓ | ✓ | ✓ |

The menu is manager-only on purpose: its prices and its allergen declarations
are what the restaurant is legally answerable for. Hiding the tab in the
console is not what enforces this — the server is, with a 403 that is written
to the audit log, because a valid token used beyond its role is worth recording
rather than only refusing. `shared/contract-suite.mjs` asks both backends the
same questions about it.

`wrangler.toml` binds the built site at `dist/web` as assets, so one deployment
serves both the API and the two apps and the tablets have no separate API
address to configure. The same two apps are also published to GitHub Pages as
a static site that reads this API across origins — `docs/PAGES.md`. Both are
the same build; only where the files are served from differs.

## Pointing the tablets at the deployment

Inside the Capacitor shell `location.origin` is `localhost`, where nothing is
listening, so an installed APK finds a backend only if it is told where one is.
Three places can say, and the first that answers wins:

1. What someone typed into the admin console (`zy_api_base` in local storage).
2. `VITE_API_BASE`, baked in when the web assets are built.
3. The origin — correct when the Worker serves the apps itself, useless in the
   APK.

So set the repository variable `API_BASE_URL` to the deployment (Settings →
Secrets and variables → Actions → Variables) and CI builds the APK pointing at
it. Leave it unset and nothing changes. To build one by hand:

```
VITE_API_BASE=https://ck.<subdomain>.workers.dev npm run build
npm run cap:sync && cd android && ./gradlew assembleDebug
```

Until a backend exists, the app falls back to the menu it ships with and says
so on the catalogue screen. Orders placed then are queued, not lost, and are
retried once it can reach a server — the product ids match, which is the whole
reason the bundled menu is generated from the seed.

## Table cards, QR and NFC

A guest's own phone is the scanner, so nothing in the app reads a camera or an
NFC tag. The entry link already carries everything: `/?table=12&k=<token>`, and
the app reads both on load, stores them, and drops the token if the table
changes.

The admin console turns those links into printable cards: **连接设置 → 生成桌卡**.
The codes are SVG at error-correction level H, because a card on a restaurant
table gets smudged and scratched, and the print stylesheet drops everything but
the sheet so "print" gives cards and nothing else.

An NFC tag holds the same string. Write the entry URL to an NTAG213 or similar
as a URI record with any tag writer; Android opens a URL record without an app
installed, so a tag and a printed code are two ways of handing over one link.
Re-write the tag after rotating a table's token, exactly as the card has to be
reprinted.

Both need the Worker deployed, because the link has to resolve to something.

## What the Worker does not do yet

- **Realtime.** `/ws` answers 501. The hub is a Node process holding sockets; on
  Workers that is a Durable Object. Until then the admin board polls, which
  TanStack Query already does for it.
- **Media upload.** `POST /api/admin/products/:id/media` answers 501. Dish
  photos are written to a disk that does not exist on Workers; they belong in
  R2. The route says so rather than appearing to succeed.
- **A shared auth rate limit.** The Worker throttles failed admin logins per
  isolate, and isolates do not share memory, so it slows a single client rather
  than enforcing a global budget. A real limit needs a Durable Object, and it
  can share the one realtime will need.
- **The print agent** still runs in the restaurant next to the printers, but it
  claims jobs over HTTP now instead of opening the database file:
  `POST /api/admin/print-jobs/claim`, then `.../:id/complete` or `.../:id/fail`.
  The lease is what stops two agents printing the same ticket.

## The trade this makes

Today the system keeps taking orders and printing tickets with the internet
down, because the database and the printers are both in the building. Once the
database is D1, an outage stops ordering and printing until it clears — during
service, on a Saturday night, that is the whole operation. Worth deciding on
deliberately rather than discovering.
