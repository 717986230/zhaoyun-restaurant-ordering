# 优化提示词库

让 AI（Claude Code 等）优化这个点餐系统时用的提示词。每条写清楚「看哪里、按什么标准、做完怎么证明」，可以直接复制使用，把 `〈〉` 里的内容换成要改的页面或功能。
格式和 `docs/motion-prompts.md` 一样：名称 + 关键要求 + 提示词。全部为本项目自写。

每条都默认遵守（不用每次重复）：

- 先读相关代码和 `docs/` 里对应的说明，再动手；只改提示词要求的范围，不顺手重构别的。
- 顾客菜单、预约、管理台、POS 四个界面都要支持中文、德语、英语三种语言，新加的文字三种都要写。
- 服务端改动 Node 服务器和 Cloudflare Worker 共用（`shared/`），两边都要能跑：`npm run server:test`、`npm run worker:test`。
- 改界面要跑对应的浏览器测试（`tests/*.spec.js`），新行为补一条测试；改完跑 `npm run build`。
- 密钥只放 Cloudflare Secret 或环境变量，不写进代码、不发到聊天。
- 每次改动写进 `CHANGELOG.md`（中文，写给店主看，不写技术细节）。

## 一、界面

### ① 页面体验审查 · UX Review
`手机 360px · 单手操作 · 3 秒找到`

> 用 360×780 的手机尺寸打开〈顾客菜单 / 预约 / 管理台某个页面〉，按顾客第一次使用的顺序走一遍主要流程，列出所有：要想一下才知道点哪里的地方、多余的文字和步骤、按钮太小（小于 44×44px）或离拇指太远的地方、浅色和深色模式下看不清的文字（对比度低于 4.5:1）。每条写清楚位置、问题、建议改法，按「影响下单或预约」「影响体验」「小问题」排序；先给清单，我确认后再改。

### ② 按钮统一 · Button System
`圆角 8px · 主按钮 1 个 · 状态 5 种`

> 检查〈页面〉里所有按钮：同一屏只能有一个主按钮（实心强调色），其余用次按钮或文字按钮；圆角、字号、内边距和项目里已有的按钮样式一致；每个按钮都要有 默认 / 悬停 / 按下 / 禁用 / 加载中 五种状态，禁用时要写明为什么不能点（例如「还差 5 积分才能预约」）。不要只靠颜色区分状态。

### ③ 手机布局 · Mobile Layout
`360 / 390 / 430 · 横屏 · 安全区`

> 在 360、390、430 宽的竖屏和横屏下检查〈页面〉：不能横向滚动，文字不能被截断或重叠，底部按钮要避开 iPhone 的安全区（env(safe-area-inset-bottom)），软键盘弹出时输入框和提交按钮仍然看得到。发现的问题直接修，并在 `tests/layout.spec.js` 里加对应的不重叠检查。

### ④ 空状态和出错 · Empty & Error States
`每个列表 · 每个请求 · 一句话 + 一个按钮`

> 找出〈页面〉里所有列表和网络请求，逐个检查三种情况：没有数据、加载中、请求失败（断网、服务器 500、权限不够）。每种都要有一句人话说明发生了什么，再给一个能做的按钮（重试、去登录、联系餐厅）；不要显示英文报错原文、错误代码或空白页。

### ⑤ 文案润色 · Copywriting
`短 · 具体 · 三种语言一致`

> 检查〈页面〉的所有文字（中文、德语、英语）：删掉客人不需要知道的内部说法和废话；按钮用动词开头说清楚点了会怎样；错误提示说清楚怎么改（「请填写手机号，不是座机号码」，而不是「格式错误」）；三种语言意思一致，德语用 Sie，数字和日期格式符合当地习惯。只改文案，列出改前改后对照。

### ⑥ 无障碍 · Accessibility
`键盘可用 · 读屏可读 · 焦点可见`

> 只用键盘（Tab、Enter、Esc）走一遍〈页面〉的主要流程：每个能点的东西都能聚焦，焦点框看得清，弹窗打开时焦点进入弹窗、Esc 关闭后回到原来的按钮；图标按钮都有 aria-label；表单错误用 role="alert" 读出来。尊重「减少动态效果」设置。

## 二、速度

### ⑦ 首屏速度 · First Load
`4G 慢网 · 首屏 < 2.5 秒 · JS 包减半`

> 用 Chrome 的慢速 4G 模拟打开顾客菜单（带桌号的扫码链接），量首屏出现菜品的时间和下载的 JS 大小（看 `npm run build` 的输出）。找出首屏用不到却一起加载的代码（预约、账户、管理功能等），改成用到时再加载；图片用合适尺寸和懒加载。给出改前改后的数字。

### ⑧ 接口速度 · API Performance
`每个请求 < 300ms · 不 N+1 · D1 一次查完`

> 检查〈接口，例如 GET /api/catalog〉在 Cloudflare D1 上的查询：有没有循环里一条条查数据库（N+1）、有没有缺索引、有没有每次都查但很少变的数据可以缓存。改成尽量一次批量查询；索引改动写成 `migrations/` 里的新迁移，并跑 `npm run d1:migrations` 检查。用合同测试保证结果不变。

### ⑨ 高峰压力 · Rush Hour
`20 桌同时 · 不丢单 · 不重复出单`

> 模拟晚上高峰：20 张桌同时扫码下单、厨房同时改状态、两个服务员同时给同一桌结账。检查会不会丢单、重复出单、重复扣积分或库存算错；找到的竞争问题用数据库事务或「只执行一次」的写法解决，并写成合同测试（`shared/contract-suite.mjs`）。

## 三、可靠和安全

### ⑩ 安全检查 · Security Review
`权限 · 输入 · 密钥`

> 检查〈功能或这次的改动〉：每个接口是否检查了身份和权限（顾客只能看自己的，员工不能做老板的事）；所有输入是否在服务端校验（长度、格式、数字范围），不能只靠前端；有没有把密钥、令牌、他人的手机号或邮箱返回给不该看的人；上传的文件是否限制了类型和大小。发现的问题按严重程度排序，先修高危的，每个都补一条测试。

### ⑪ 断网和重试 · Offline & Retry
`店里 WiFi 断 10 秒 · 不重复下单`

> 模拟店里网络断开 10 秒再恢复：POS 和顾客菜单正在下单、结账、打印时会发生什么？要做到：断网时明确提示、恢复后自动重试；同一笔订单不会因为重试被下两次（用 clientRequestId 之类的去重）；打印失败的单子能在管理台看到并重打。

### ⑫ 测试补齐 · Test Coverage
`每个改动 · 正常 + 出错 + 边界`

> 为〈功能〉补测试：正常流程一条，常见出错（没权限、数据不对、重复提交）各一条，边界情况（0、最大值、跨午夜、时区）各一条。服务端写在合同测试里，保证 Node 和 D1 两边都跑；界面写在 Playwright 测试里。不要为了让测试通过而跳过或删掉已有的测试。

## 四、生意

### ⑬ 下单转化 · Order Conversion
`扫码到下单 ≤ 4 步 · 每步少一个决定`

> 从客人扫桌上二维码开始，数一数到成功下单要点几次、要做几个决定。找出可以省掉的步骤（例如必须先登录、反复确认、不必要的弹窗），以及能让客人多点一份的地方（推荐、套餐、加料），但不要用打扰客人的方式。给出建议清单，标注哪些需要我决定。

### ⑭ 积分和预约规则检查 · Loyalty Rules
`算得对 · 讲得清 · 钻不了空子`

> 检查积分和预约的全部规则（注册送积分、每次预约扣分、取消退回、首次到店送分、爽约扣分、兑换菜品）：每种情况算出来的积分对不对；客人在页面上能不能看懂规则；有没有办法刷积分（反复注册、取消再预约、同一个人多个号）。列出漏洞和修法，修完补测试。

### ⑮ 店主看得懂 · Owner Friendly
`不用培训 · 一句话说明 · 改错能撤回`

> 以不懂技术的店主身份打开管理台的〈某个设置页〉：每个设置项是否有一句话说明它影响什么、默认值是否合理、改错了能不能一键恢复、保存后有没有明确提示。把需要看说明书才会用的地方列出来并改掉。

## 怎么用

- 一次只给一条，改一个页面或一个功能，效果比「全面优化一下」好得多。
- 想先看问题再决定改不改，在提示词后面加一句：「先只列问题，不要改代码」。
- 想直接改并上线，加一句：「改完跑测试、写 CHANGELOG、开 PR」。
- 动效相关的用 `docs/motion-prompts.md`，可以一起用，例如「按 ① 审查菜单页，动效按 ③ 和 ⑤」。
